# AgileCampus 工作报告

面向课程项目的敏捷协作平台

## 一、总体情况

本项目做的是一个面向高校课程项目的敏捷协作平台，名字叫 AgileCampus。它要解决的问题是：课程项目里任务散落在群聊和文档中，谁在做什么、做到哪一步没有统一视图；教师只能在结课时看到结果，无法在过程中干预质量；通用工具（Trello、飞书项目之类）缺少课程场景需要的“小组长初审、教师终审”两级把关，也没有缺陷分级、燃尽图和复盘留档。

系统把团队组建、项目拆解、任务认领、过程评审、进度可视化、迭代复盘串成一条完整链路。目前共有 21 张数据表、19 个页面、23 个接口，TypeScript 源码约 1.26 万行，自动化测试 267 项。

下面按功能模块说明具体做了什么，再说明技术实现、测试验证与已知不足。

## 二、账号、团队与权限

系统支持邮箱密码与飞书扫码两种登录方式，密码使用 bcrypt 哈希存储，会话使用 JWT。用户注册后可凭邀请码加入团队，邀请码在页面上默认折叠，点开才显示并可一键复制，避免投屏时泄露。

团队内有管理员、教师、小组长、学生四种角色。成员页支持修改角色、移除成员，成员本人可以退出团队。这里做了一个“末位管理员保护”：无论是把最后一名管理员降级、移除他，还是他自己退出，三条路径都会被拒绝，避免团队出现无人可管理的情况。

权限的划分方式是按“动作”而不是按“页面”。同一张任务卡，学生和小组长能改，教师只能看；提交评审只能由任务负责人发起；初审退回小组长可以做，终审通过只有教师和管理员能做。所有校验都落在服务端，页面只是不显示没有权限的按钮，直接构造请求同样会被拒绝。

## 三、项目与任务

项目隶属于团队，可以设置起止日期和描述，并带有项目档案页——任务讨论中被标记为“决策”或“交付”的重要评论会自动归档进去，形成交付物清单。

任务是最小工作单位，支持多人负责、父子任务（子任务）、完成-开始依赖、标签、开始与截止日期、优先级，以及后面为收敛期新增的预估工时、阻塞标记与阻塞原因。有依赖关系时，前置任务未完成，后置任务在看板上会置灰并带锁图标，拖到“已完成”会被拒绝并提示还差哪几个前置任务。

任务的展示有三种视图。看板按列分组，支持按状态、负责人、优先级、里程碑、缺陷状态五种维度切换，拖拽卡片即可改字段，采用乐观更新，失败会回滚；列内还可以用上下箭头调整顺序。列表视图按状态、优先级、截止日排序，适合快速核对与手机屏幕。甘特视图按时间轴展示排期，支持日、周、月三档缩放，标出里程碑、依赖连线和今天的位置。

筛选条件包含负责人、优先级、标签、里程碑、是否逾期、是否只看缺陷，全部写在网址参数里，因此可以复制链接分享，刷新也不会丢。

## 四、评审流程

这是本系统最核心的业务逻辑。任务在“待办、进行中、已完成”之外增加了“待评审”和“已退回”两档，流转只允许四条路径：进行中提交评审进入待评审；待评审被教师通过进入已完成；待评审被退回进入已退回；已退回修改后重新提交回到待评审。其它跳跃一律拒绝，例如待办直接提交、已完成再退回。

操作权限按角色区分：提交评审只能由任务负责人发起；退回可以由教师、管理员和小组长操作；终审通过只有教师和管理员可以。小组长打开待评审任务时，页面上只有“退回修改”按钮，并明确提示“终审通过由教师操作”。退回必须填写原因，通过可以附评审意见，两者都会自动写入批注列表永久留痕。

任务详情页有独立的评审区块与批注列表，师生可以互相回复。评审结果会同时发两类通知：站内红点和飞书卡片，卡片里带任务名、项目名、评审人和意见，接收人是全体负责人但排除评审人自己。另外保留了原有的依赖校验：存在未完成的前置任务时不能通过评审，与看板的完成口径保持一致。

## 五、迭代与燃尽图

为了最后一周的收敛，增加了“迭代”这个单位。可以为项目创建迭代，填名称、目标、起止日期；任务可以归入某个迭代，迭代页还提供“把未排期任务一键拉进本迭代”的批量操作，避免一条条点进详情去挂。

燃尽图按预估工时计算：理想线从总工时线性下降到零，实际线表示每天结束时仍未完成的任务工时之和，用竖线标出今天。实际线长期高于理想线，说明任务拆得不够细或估时偏低。图下方给出任务数、已完成数、总工时、剩余工时四个数字，站会可以直接播报。没有填估时的任务不计入曲线，页面会提示有多少条未估时，避免曲线失真。

## 六、缺陷管理

任务增加了“功能任务”与“缺陷卡”两种类型。缺陷卡带有三级严重度（阻断级、重要级、优化级）、四态生命周期（待处理、处理中、已修复、验证通过），以及一个“关联原始任务”字段，方便追溯是在哪个任务上发现的。

看板上缺陷卡带红色徽章并显示严重度，筛选栏有“仅看缺陷”开关，分组依据里还能按缺陷状态分成五列（含非缺陷列），拖拽即可推进缺陷状态。这样在最后一周集中修缺陷时，阻断级还剩几个、哪些已修待验证，一眼就能看到。

## 七、通知与外部集成

通知分两层。站内通知是导航栏的红点与通知列表，支持按未读统计。飞书通知是交互卡片，覆盖新任务指派、任务完成、评审通过或退回三种场景，卡片带任务名、项目名、负责人、截止日期和“查看详情”按钮，点击可直接跳到平台对应任务。

逾期提醒走定时任务接口，扫描临期与逾期任务，按负责人聚合成一张日报，避免每个任务单独发一条把消息刷屏。飞书账号需要用户先在设置页完成绑定，未绑定的用户不会收到推送，也不会影响网页端的正常使用。

## 八、AI 助手

AI 助手定位不是聊天玩具，而是操作入口。它支持用自然语言建任务、拆解任务、批量调整任务。实现方式是把项目快照交给模型，快照里包含成员、里程碑、任务的名称与编号，以及“今天是几号”，让模型能够正确理解“下周五之前”这类相对时间。模型调用工具后不直接写库，而是生成一份变更草案，前端渲染成可确认的卡片，用户确认后才真正落库。

为了防止覆盖别人的修改，批量写入采用乐观锁：提交时带上读取时的更新时间，版本不一致就拒绝并提示刷新重试。开发中遇到两个问题：一是模型会口头说“已经拟好草案”却不真正调用工具，必须在提示词里明确“只有调用工具才会产生草案”；二是模型过度盘问，一句“帮我建个任务”会追问十几轮，需要用具体示例约束它先动手。这两个问题都写进了提示词与文档。

## 九、数据导出与复盘

导出提供两份 CSV。任务清单有 17 列，包含类型、缺陷等级、预估工时、迭代、负责人、完成时间等；迭代记录包含任务数、完成数、总工时与剩余工时。文件带 BOM 头，用 Excel 双击打开中文不会乱码，方便整理成周报或答辩材料。

复盘页用于每次迭代结束后的记录，分四栏：做得好的、待改进的、改进措施、踩坑点，可以关联到具体迭代。历史复盘按时间倒序列出，提交材料时整页复制即可。

## 十、技术实现要点

系统基于 Next.js 16 的 App Router 实现，页面用服务端组件直出减少接口层，表单提交用 Server Actions。数据库是 PostgreSQL 16，ORM 用 Drizzle，表结构由代码定义后同步到数据库，改字段时类型检查会直接报错。鉴权用 Auth.js 的 JWT 会话，支持邮箱密码与飞书两种登录。

所有写操作的鉴权收敛到三个领域层函数：任务写权限、团队角色校验、项目访问校验。页面层不再重复判断“是不是管理员”，新增接口时不会漏鉴权，也方便写集成测试直接验证权限边界。

中间件只负责一件事：根据登录令牌里的“记住我”标记重写 Cookie 的过期属性。这里踩过一个坑：中间件运行在 Edge Runtime，如果引入数据库或 Node 的加密模块，整站页面都会 500，只有接口还能用。最终改成只解码 JWT、不构建完整鉴权实例，问题消失。

用户级别的 API 密钥用 AES-256-GCM 加密后存库，密钥由服务端环境变量派生；数据库里只存令牌的哈希，明文只在生成时返回一次。

## 十一、测试与验证

测试分三层。纯函数单元测试覆盖筛选、分组、燃尽计算这些不依赖数据库的逻辑；领域层集成测试直连独立的测试库，验证权限、状态机、事务与通知；页面与接口冒烟则通过真实启动服务，检查关键路径的返回码与页面文案。测试库与开发库分离，每次运行前统一清空，保证用例可重复。

当前共有 34 个测试文件、267 项用例，其中 265 项通过、2 项跳过。跳过的两项是需要真实模型密钥的联调用例，避免每次回归都消耗额度，需要时可以通过环境变量开启。类型检查与代码规范检查均为零错误。

评审相关的关键用例包括：负责人提交评审、待办直接提交被拒、非负责人提交被拒、教师终审通过并写入完成时刻、小组长能退回但不能终审、学生不能退回、退回原因必填、已退回可重提、已完成不能再退回、前置任务未完成不能通过、空批注被拒、跨任务回复被拒。此外还覆盖了末位管理员保护与燃尽图的单日边界。

手工验收覆盖了注册登录、建团队加成员、建项目建任务、三视图切换、评审全流程、迭代与燃尽、CSV 导出这些主路径。

## 十二、部署与使用

数据库用 Docker Compose 启动 PostgreSQL 16，数据通过数据卷持久化。初始化流程是先启动数据库，再同步表结构，最后启动服务。开发模式直接运行开发服务器，生产模式先构建再启动，也可以用仓库里的 Dockerfile 构建独立镜像。

日常备份用数据库自带的导出工具生成 SQL 文件，恢复时回灌即可。表结构变更通过迁移工具同步，新增字段与枚举值都有对应脚本，历史数据也用一次性脚本补齐过——例如给已完成的任务回填完成时刻，保证燃尽图对旧数据同样成立。

## 十三、已知不足

评审通过后无法撤回，终态设计如此，误操作只能改库。批注本身不触发通知，只有评审结果会通知，讨论场景可能漏看。系统没有实时同步，两个人同时打开页面时，一方提交评审后另一方需要刷新才能看到。项目进度页按团队分组，教师目前看不到“所有团队一屏”的跨组总览。此外没有附件能力，交付物只能写文字说明。

这些不足已经记录在案的下一步计划里，优先级从高到低依次是：批注提及与通知、全局搜索、跨团队总览、附件上传、基于 SSE 的实时刷新。

## 十四、小结

这个项目做的不是又一个看板，而是把课程项目的流程结构化：任务有状态机、评审有留痕、进度有曲线、复盘有模板。技术上验证了服务端状态机、乐观锁、AI 工具调用与多端通知在中小型协作系统里的可行性；工程上把测试、部署和复盘纳入日常，让最后的收敛期不再是通宵补功能，而是有数据支撑的取舍。

过程中也放弃了一些看起来更炫的方向，比如微服务、实时协作和附件。这些取舍不一定让演示更漂亮，但让系统在多人同时使用时不容易翻车，这也是敏捷开发真正要解决的问题。
