## 一、这一阶段要解决什么

第一阶段解决了「教师能看到全组进度」，但看不到**过程质量**：学生交上来的任务只有「已完成/未完成」两态，教师既不能留意见，也不能退回重做；所有把关责任压在教师一个人身上，任务一多就审不过来。

这一阶段把「评审」做成一条**有状态、有留痕、有通知**的流水线，并把初审下放给小组长：

- 学生做完 → 提交评审
- 小组长/教师 → 退回（必须写原因）或教师终审通过
- 批注与评审意见永久留痕，谁在什么时候说了什么，可追溯

## 三、关键设计决定

**1. 状态机放在服务端，而不是靠前端隐藏按钮。**
前端只是不显示无权限的按钮，真正的跃迁校验在 `submitForReview / approveReview / rejectReview` 里：角色不对、状态不在前置态、前置任务未完成，一律抛错。同时 `updateTask` 明确拒绝直接写 `review/rejected`，堵住「绕过评审直接改状态」这条路。

**2. 看板上的评审两列不可拖拽。**
评审是带责任的流转，拖拽是零成本的误触。待评审/已退回两列只读，必须进任务详情点按钮，且退回必须填原因。

**3. 批注单独建表，不复用评论表。**
评论是讨论（可编辑、可标记重要、可删除），批注是凭证（评审意见/退回原因永久留痕）。两者生命周期不同，混在一张表里迟早要为「能不能删评审意见」打架。

**4. 小组长有初审权、没有终审权。**
文档的权限表是刻意的：退回是「让学生改」，风险低；通过是「认可交付」，风险高。小组长看到待评审任务时，页面会提示「终审通过由教师操作」。

## 六、已知缺口

1. **看板列内排序**仍按创建时间，`sort_order` 字段未接入拖拽排序——想手动调「先做哪个」目前做不到。
2. **成员管理只有改角色**：不能移除成员、不能退出团队、不能转让管理员；最后一名管理员仍可把自己降级（`BACKLOG` 有记）。
3. **评审通过后无法撤回**：终态设计如此，但误操作只能改库。
4. **批注无通知**：批注本身不触发飞书，只有评审结果触发；讨论场景可能漏看。
5. **无实时同步**：两人同时开页面，一方提交评审后另一方要刷新才看到。

## 附：3 分钟演示动线

1. 团队 → 成员：把一名学生设为「小组长」
2. 小组长登录 → 项目看板 → 打开一个进行中任务 → 提交评审（任务进入「待评审」列）
3. 小组长打开该任务：只有「退回修改」，页面提示终审由教师操作 → 填原因退回
4. 学生重新提交 → 教师账号打开 → 「通过评审」并写评审意见
5. 任务进「已完成」，批注区能看到「退回原因」与「评审意见」两条留痕
6. 回项目页看燃尽图与导出 CSV
